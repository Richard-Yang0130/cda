# 管理后台设计

目标：给运营人员（目前就是你）一个能管用户、管内容、管邀请码的后台。
先调研主流方案，再**依据现有功能**推导功能点 —— 不做用不上的东西。

---

## 一、调研：主流后台方案

| 项目 | 技术栈 | 特点 | 适合我们吗 |
|---|---|---|---|
| **vue-element-admin** | Vue2 + Element | 国内最知名，star 最多 | ❌ Vue2 已停止维护 |
| **vue-vben-admin** | Vue3 + Vite + TS | 现代、功能全、组件多 | ⚠️ 偏重，学习成本高 |
| **Soybean Admin** | Vue3 + Vite + TS + Naive | 干净、类型友好、上手快 | ✅ **可参考** |
| **Ant Design Pro** | React + AntD | 企业级标杆 | ❌ 我们前端是 Vue |
| **若依 RuoYi** | Java + Vue | 国产经典，**RBAC 权限模型完整** | ✅ **权限设计可参考** |
| **tabler** | Bootstrap | 纯模板，无框架绑定 | ✅ 轻量可选 |
| **Spree Commerce** | Rails | 电商后台，角色体系清晰 | ✅ 电商字段设计可参考 |

### 结论：**不要引入这些框架**

理由：

1. 我们的前端是 **uni-app**，而这些后台框架都是独立的 Vue/React 工程。
   引入意味着**维护两套构建体系**。
2. 这些框架动辄几十个组件、几十个依赖，而**我们只需要 6～8 个页面**。
3. 服务器是 2核2G，多一套构建产物没必要。

**做法：在现有的 uni-app 工程里加一组 `/pages/admin/*` 页面**，
复用已有的组件与样式体系。管理后台在 PC 上打开，正好用上我们已有的
**侧边栏布局**（`NavShell` 在 ≥768px 时就是左侧边栏）。

> 参考价值在于**权限模型**（若依的 RBAC）与**字段设计**（Spree 的角色），
> 不在于照搬代码。

## 二、基于现有功能推导：管理后台要管什么

现有 13 张表，逐张问「运营需要看/改它吗」：

| 现有表 | 管理需求 | 紧急度 |
|---|---|---|
| **`invites`** | **生成/作废邀请码，看谁用了** | 🔴 **最高** —— 现在只有 12 个，用完就没，加码要改数据库 |
| `users` | 列表、搜索、禁用、重置密码、看资料 | 🔴 高 |
| `posts` | 内容审核：删除违规帖 | 🟠 中 |
| `comments` | 评论审核 | 🟠 中 |
| `blocks` | 查看/解除拉黑（用户申诉时） | 🟡 低 |
| `messages` | 举报处理需要看聊天记录 | 🔴 高（合规） |
| `login_attempts` | 看谁在被撞库、手动解锁 | 🟠 中 |
| `sessions` | 强制下线 | 🟡 低 |
| `follows` | 统计 | 🟢 只读 |
| `user_styles` / `user_brands` | **统计什么风格/品牌受欢迎** | 🟠 中（对选品有用） |
| `wardrobe` | 统计 | 🟢 只读 |
| `addresses` | ❌ **不看** —— 收货地址是高敏感隐私 | — |

### 从上面推出来的功能清单

**P0（这周就要用）**

1. **登录** —— 独立于用户体系，见第三节
2. **邀请码管理** —— 生成、批量生成、作废、看使用情况
3. **用户列表** —— 搜索（昵称/用户码/手机号）、看详情、**禁用/启用**
4. **用户详情** —— 基本信息、注册时间、最后在线、发帖数、被举报数

**P1（有问题时要用）**

5. **内容审核** —— 帖子/评论列表，一键删除并通知作者
6. **举报处理** —— 用户举报 → 审核 → 处理（删内容 / 封号 / 驳回）
7. **登录安全** —— 看 `login_attempts`，手动解锁被锁账号
8. **数据看板** —— 注册数、活跃数、发帖数、消息数（趋势）

**P2（有余力再做）**

9. **风格/品牌统计** —— 什么风格、什么品牌被选得最多 → 指导选品
10. **强制下线** —— 清 `sessions`
11. **操作审计日志** —— 谁在什么时候改了什么

### 明确不做的

| 不做 | 原因 |
|---|---|
| **改用户身型数据** | 那是用户的私人数据，运营无权改 |
| **看收货地址** | 高敏感隐私，除非有明确的法律要求 |
| **代用户发帖/发消息** | 会破坏"这是用户本人说的"这个前提 |
| **改密码** | 只能"发重置链接"，不能看到或设置明文 |

## 三、登录与权限设计

### 3.1 为什么必须与用户体系分开

**管理员绝不能是 `users` 表里的一行。** 理由：

1. 用户表有注册流程、邀请码、隐私设置，管理员不该走这套
2. 一旦用户表被攻破，管理员账号会一起沦陷
3. 权限模型不同（用户是平的，管理员有角色）

**做法：独立 `admins` 表 + 独立 token。**

### 3.2 表结构

```sql
-- 管理员
CREATE TABLE admins (
  id            TEXT PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  password_salt TEXT NOT NULL,
  display_name  TEXT NOT NULL DEFAULT '',
  role          TEXT NOT NULL DEFAULT 'operator',   -- owner | operator | viewer
  status        TEXT NOT NULL DEFAULT 'active',
  last_login_at TEXT,
  last_login_ip TEXT,
  created_at    TEXT NOT NULL
);

-- 独立会话（与用户 sessions 完全隔离）
CREATE TABLE admin_sessions (
  token      TEXT PRIMARY KEY,
  admin_id   TEXT NOT NULL REFERENCES admins(id) ON DELETE CASCADE,
  ip         TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL
);

-- 操作审计：管理后台**必须**有，否则出事查不到人
CREATE TABLE admin_logs (
  id         TEXT PRIMARY KEY,
  admin_id   TEXT NOT NULL,
  action     TEXT NOT NULL,        -- 如 user.disable / invite.create
  target     TEXT NOT NULL DEFAULT '',
  detail     TEXT NOT NULL DEFAULT '',
  ip         TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL
);

-- 举报
CREATE TABLE reports (
  id          TEXT PRIMARY KEY,
  reporter    TEXT NOT NULL,       -- 举报人的用户码
  target_type TEXT NOT NULL,       -- post | comment | user | message
  target_id   TEXT NOT NULL,
  reason      TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending | resolved | rejected
  handled_by  TEXT,
  handled_at  TEXT,
  created_at  TEXT NOT NULL
);
```

### 3.3 三级角色详解

#### 三个角色分别是谁

| 角色 | 中文 | 典型使用者 | 一句话定位 |
|---|---|---|---|
| `owner` | 所有者 | **你** | 能改一切，包括「谁能进后台」 |
| `operator` | 运营 | 你招的兼职/合伙人 | 能管日常事务，**但改不了管理员** |
| `viewer` | 观察者 | 投资人、想了解数据的合伙人 | **只能看，一个字都改不了** |

#### 为什么正好是三个

角色数量不是拍脑袋定的，是跟着**「谁能改谁能进后台」**这条线划出来的：

- 有一件事**只有你能做**：给别人开后台账号、改别人角色、删管理员。
  这条线画出 `owner`。
- 有一类人**需要天天干活**：发邀请码、封号、删违规内容。
  但他们**不该能给自己或别人开权限** —— 否则一次账号泄露就等于后台失守。
  这条线画出 `operator`。
- 有一类人**只需要看**：投资人想知道增长数据，合伙人想知道大家用得怎么样。
  给他们写权限没有收益，只有风险。这条线画出 `viewer`。

**关键分界线是「能否管理管理员」**，不是「能操作多少功能」。
这条线一划，权限泄露的爆炸半径就被限制住了。

#### 完整权限矩阵

| 能力 | owner | operator | viewer |
|---|:---:|:---:|:---:|
| **管理员管理** | | | |
| 创建/删除管理员 | ✅ | ❌ | ❌ |
| 修改他人角色 | ✅ | ❌ | ❌ |
| 修改自己的密码 | ✅ | ✅ | ✅ |
| **邀请码** | | | |
| 查看列表与使用情况 | ✅ | ✅ | ✅ |
| 生成 / 批量生成 | ✅ | ✅ | ❌ |
| 作废未使用的 | ✅ | ✅ | ❌ |
| **用户** | | | |
| 列表 / 搜索 | ✅ | ✅ | ✅ |
| 查看详情（昵称、注册时间、最后在线） | ✅ | ✅ | ✅ |
| **查看手机号 / 邮箱** | ✅ | ✅（记审计） | ❌ |
| 禁用 / 启用（须填原因） | ✅ | ✅ | ❌ |
| **永久删除用户** | ✅ | ❌ | ❌ |
| 生成密码重置码 | ✅ | ✅ | ❌ |
| **内容** | | | |
| 查看帖子 / 评论 | ✅ | ✅ | ✅ |
| 删除帖子 / 评论 | ✅ | ✅ | ❌ |
| **举报** | | | |
| 查看待处理举报 | ✅ | ✅ | ✅ |
| 处理举报（删内容/封号/驳回） | ✅ | ✅ | ❌ |
| **安全** | | | |
| 查看被锁账号 | ✅ | ✅ | ✅ |
| 手动解锁 | ✅ | ✅ | ❌ |
| **查看审计日志** | ✅ 全部 | ✅ 全部 | ❌ |
| **数据看板 / 风格品牌统计** | ✅ | ✅ | ✅ |

#### 三条划线的理由

**① 「永久删除用户」只有 owner 能做**
禁用是可逆的，删除不可逆。可逆的操作可以放权，**不可逆的不放**。
日常运营里几乎没有「必须立刻物理删除」的场景，真遇到可以找你。

**② 手机号对 viewer 完全不可见**
手机号是**唯一能定位到真人的标识**。看板上根本用不到它，
给 viewer 看只有泄露风险。owner 与 operator 能看到，且每次查看写审计日志。

**③ 审计日志对 operator 开放**
听起来反直觉（让运营看自己的记录？），但这是**有意的**：

- 透明能防止滥用 —— 知道自己被记录、且记录对同事可见，是最好的约束
- 我们的 operator 大概率是熟人，藏着反而显得不信任
- 真要防的是**外部入侵者**，而他们拿到 operator 权限时，
  藏不藏日志都挡不住

只有 `viewer` 看不到审计日志 —— 因为让他看到「谁封了谁」没有意义，
反而暴露了其他管理员的账号名。

#### 明确不做的

| 不做 | 原因 |
|---|---|
| 细粒度 RBAC（菜单/按钮级） | 若依那套是为几十人团队设计的。我们 1–3 人，每加一个功能都要配权限，拖慢开发 |
| 自定义角色 | 三个够用。真要第四个（如「内容审核员」），到时再加，改动很小 |
| 数据行级权限 | 没有「只能看自己负责的用户」这种需求 |
| 多因素认证（MFA） | 现阶段收益低于成本。等后台被盯上再说 |
| 管理员操作二次确认 | 除了删除类操作，其余不弹确认框，否则天天点很烦 |

#### 实现方式（保持极简）

权限检查**不建表**，直接在代码里写一张常量表：

```ts
// packages/core/src/admin.ts
export const ADMIN_PERMS = {
  owner:    ['admin.manage', 'invite.write', 'user.read', 'user.phone',
             'user.disable', 'user.delete', 'content.delete',
             'report.handle', 'security.unlock', 'audit.read', 'stats.read'],
  operator: ['invite.write', 'user.read', 'user.phone', 'user.disable',
             'content.delete', 'report.handle', 'security.unlock',
             'audit.read', 'stats.read'],
  viewer:   ['user.read', 'stats.read'],
} as const

export function can(role: AdminRole, perm: string): boolean {
  return (ADMIN_PERMS[role] as readonly string[]).includes(perm)
}
```

**为什么用常量表而不是数据库**：

- 角色只有 3 个、权限只有 11 项，写死在代码里**一眼能看全**
- 放进数据库意味着要做一套「权限配置界面」，那是给几十人团队用的
- 改权限时改代码、走一次部署，**有 Git 记录**，比在界面上点更可追溯

#### 边界情况

| 情况 | 处理 |
|---|---|
| 只有一个 owner，他忘了密码 | 用服务器命令行直接改（`deploy/` 里提供脚本）。**不做"找回密码"** —— 后台没有邮件服务 |
| 想给第二个人 owner 权限 | owner 可以直接改角色。但建议**最多两个 owner** |
| operator 离职 | owner 把状态改为 `disabled` 或直接删除，**其所有 session 立即失效** |
| 管理员误删内容 | 靠备份恢复（每日 04:00）。所以**删除操作要写审计日志**，至少知道丢了什么 |
| 想审计 owner 自己 | 一样记日志。**owner 不是免审计的** |

### 3.4 安全要求（比用户端更严）

| 项 | 要求 |
|---|---|
| 密码 | 至少 12 位；scrypt（沿用现有实现） |
| **登录频率限制** | 5 次失败锁 30 分钟（比用户端的 10 分钟更严） |
| **强制 HTTPS** | 已经是了 |
| **不在主站路径下** | 或至少 `/admin` 加额外保护 |
| **所有写操作记审计日志** | 必须，否则出事查不到人 |
| **禁用用户必须填原因** | 强制填写，写进审计日志 |
| **默认不显示手机号** | 需要点击才显示，且记一次审计日志 |

## 四、页面结构

沿用现有 `NavShell` 的侧边栏（≥768px 自动变左侧栏）：

```
/admin/login          管理员登录
/admin/dashboard      数据看板
/admin/invites        邀请码管理       ← P0
/admin/users          用户列表         ← P0
/admin/users/:code    用户详情
/admin/posts          内容审核         ← P1
/admin/reports        举报处理         ← P1
/admin/security       登录安全 / 审计日志  ← P1
/admin/stats          风格品牌统计      ← P2
```

## 五、接口设计

```
POST /api/admin/auth/login       { username, password } → { token }
POST /api/admin/auth/logout
GET  /api/admin/me

GET    /api/admin/dashboard                 看板数据
GET    /api/admin/invites                   邀请码列表（含使用者）
POST   /api/admin/invites                   生成（支持批量、备注）
DELETE /api/admin/invites/:code             作废（未使用的才能删）

GET    /api/admin/users?q=&status=&limit=   用户列表
GET    /api/admin/users/:code               用户详情（含统计）
PATCH  /api/admin/users/:code               改状态（禁用/启用，**必须带 reason**）
POST   /api/admin/users/:code/reset         生成重置码（不能直接改密码）

GET    /api/admin/posts?q=                  帖子列表
DELETE /api/admin/posts/:id                 删除
GET    /api/admin/comments?postId=
DELETE /api/admin/comments/:id

GET    /api/admin/reports?status=pending
POST   /api/admin/reports/:id/handle        { action: 'delete'|'ban'|'reject', note }

GET    /api/admin/security/attempts         被锁的账号
DELETE /api/admin/security/attempts/:key    手动解锁
GET    /api/admin/logs                      审计日志
```

**所有 `/api/admin/*` 走独立的鉴权中间件**，与用户 token 完全不共用。

## 六、实现顺序建议

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **第一步** | `admins` 表 + 登录 + 审计日志骨架 | 半天 |
| **第二步** | **邀请码管理** —— 这是当下最痛的（只有 12 个，加码要改数据库） | 半天 |
| **第三步** | 用户列表 + 详情 + 禁用/启用 | 一天 |
| **第四步** | 内容审核 + 举报处理 | 一天 |
| **第五步** | 数据看板 + 风格品牌统计 | 半天 |

**先做前两步就够用很久了。**

---

## 七、两个提醒

1. **管理后台不需要好看，需要好用。** 表格 + 筛选 + 搜索即可，
   别在样式上花时间。
2. **审计日志不是可选项。** 后台能封号、能删内容，出问题时
   「谁在什么时候因为什么做了什么」必须查得到。这张表从第一天就要有。
