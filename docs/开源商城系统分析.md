# 五个开源商城系统分析 —— 聚焦注册 / 登录 / 用户系统

调研目的：**P0-2 用户系统要对标成熟产品**，避免自己拍脑袋设计。
本机网络下 GitHub 网页可访问、但 git 操作不通，所以以下内容来自
仓库 README / 公开资料检索 + 各项目通用实现方式，
**具体字段与流程建议上线前到对应仓库核对一遍**。

---

## 一、选的五个，以及为什么选它们

| # | 项目 | 技术栈 | 定位 | 为什么入选 |
|---|---|---|---|---|
| 1 | **macrozheng/mall** | Java + SpringBoot + MyBatis | 学习型 B2C 商城 | 国内 star 最高的商城项目，**用户体系是最标准的教科书实现** |
| 2 | **linlinjava/litemall** | SpringBoot + Vue + 微信小程序 | 小而全 | 一个仓库含管理后台/商城/小程序三端，**多端账号打通**做得清楚 |
| 3 | **newbee-ltd/newbee-mall** | SpringBoot + Vue | 新手向 | 代码量小、结构清晰，**适合逐行读它的登录态设计** |
| 4 | **CRMEB** | ThinkPHP / Java 双版本 | 商用级多端 | **功能最全**：多端 + 分销 + 会员等级 + 直播，用户体系也最复杂 |
| 5 | **ShopXO** | ThinkPHP | 企业级免费开源 | 偏「开箱即用」，**权限与角色体系**比前几个细 |

> 前三个是**学习/二次开发**导向，后两个是**直接商用**导向。
> 两种取向在用户系统上的差别很明显，下面会标注。

## 二、注册方式对比

| 能力 | mall | litemall | newbee-mall | CRMEB | ShopXO |
|---|---|---|---|---|---|
| 手机号 + 短信验证码 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 账号密码 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 邮箱注册 | ✅ | ➖ | ➖ | ✅ | ✅ |
| 微信小程序一键登录 | ➖ | ✅ | ➖ | ✅ | ✅ |
| 微信公众号网页授权 | ➖ | ✅ | ➖ | ✅ | ✅ |
| App 微信/QQ 登录 | ➖ | ➖ | ➖ | ✅ | ➖ |
| **注册即送积分/优惠券** | ➖ | ➖ | ➖ | ✅ | ✅ |
| **邀请码 / 推荐人绑定** | ➖ | ➖ | ➖ | ✅ | ✅ |

### 值得注意的差异

- **学习型项目（mall / newbee-mall）几乎只有「手机号或账号密码」**，
  因为它们的目标是讲清 JWT 登录态，不是拉新。
- **商用型（CRMEB / ShopXO）注册链路即营销链路**：
  注册送券、邀请码绑定上下级关系（为分销铺路）。
  → 我们**不要**这一套：涉及分销就接近经营性，个人主体做不了。

## 三、登录与登录态

| 能力 | 说明 |
|---|---|
| JWT + 拦截器 | mall / newbee-mall / litemall 都用 **JWT 存 token，前端放 localStorage，请求头带 Authorization** |
| Session + Redis | ShopXO / CRMEB 偏传统，用 **Session + Redis** 做多端共享登录态 |
| Token 刷新 | **五个项目里只有 CRMEB 和 ShopXO 做了**；学习型项目多是「过期就重登」 |
| 多端登录互斥 | 商用型有「同一账号只能一台设备在线」的开关；学习型没有 |
| 记住我 / 自动登录 | 普遍有 |
| 登录失败次数限制 | **只有 ShopXO / CRMEB 有**（防撞库）；学习型项目基本没有 |

**结论**：登录态本身不难，**难的是安全策略**（刷新、限流、互斥）。
我们 demo 阶段可以简化，但**要在接口层预留**，否则以后加很痛。

## 四、用户体系（重点）

### 4.1 用户资料字段

五个项目**共同的必备字段**：

```
id / 用户名 / 昵称 / 手机号 / 密码哈希 / 头像 / 性别
生日(可选) / 注册时间 / 最后登录时间 / 状态(正常/禁用)
```

**我们已有的**（注册流程 6 步）：昵称、性别、生日、头像、身型、风格、品牌。
**我们缺的**：最后登录时间（已建模但未在列表展示）、账号状态。

### 4.2 会员等级

| 项目 | 做法 |
|---|---|
| mall | 有「会员等级」表，按**成长值**升级，等级影响折扣 |
| litemall | **无等级**，只有普通用户 |
| newbee-mall | **无等级** |
| CRMEB | 等级 + **付费会员卡** + 等级专属价 |
| ShopXO | 等级 + 会员折扣 + 等级专享商品 |

**取值**：等级体系是**为了促销**，不是为了用户。我们做的是「衣橱驱动」的购物 App，
**早期不需要等级**；等有复购数据再说。

### 4.3 积分 / 余额 / 优惠券

| 项目 | 积分 | 余额 | 优惠券 |
|---|---|---|---|
| mall | ✅ 积分记录 | ➖ | ✅ |
| litemall | ✅ | ➖ | ✅ |
| newbee-mall | ➖ | ➖ | ➖ |
| CRMEB | ✅ | ✅ 充值 | ✅ |
| ShopXO | ✅ | ✅ | ✅ |

**余额与充值 = 资金池 = 强监管**，个人主体**绝对不要碰**。
积分与优惠券相对安全，但也属于营销工具，可以后置。

### 4.4 收货地址

**五个项目全都有**，且都是标准的「省市区三级联动 + 默认地址」。
这是我们**该补的**——购物 App 没有地址不成立。
字段：收货人 / 手机号 / 省市区 / 详细地址 / 是否默认。

### 4.5 收藏与浏览足迹

| 项目 | 商品收藏 | 浏览足迹 |
|---|---|---|
| mall | ✅ | ✅ |
| litemall | ✅ | ✅ |
| newbee-mall | ➖ | ➖ |
| CRMEB | ✅ | ✅ |
| ShopXO | ✅ | ✅ |

**我们已有入口（我的收藏/浏览历史）但无数据结构**，需要补。

### 4.6 社交关系

| 能力 | 有做的项目 | 说明 |
|---|---|---|
| 关注 / 粉丝 | **基本都没有** | 商城系统普遍不做社交 |
| 私聊 / 站内信 | **都没有** | 只有「客服会话」（CRMEB 有） |
| 拉黑 | 无 | — |

**这是我们的差异点**：商城系统不做社交，而我们要做「穿搭社区 + 购物」。
**所以用户系统这块，我们不能照抄商城，反而更接近社交产品**（微博/小红书那类）。
→ 关注、粉丝、私聊、拉黑、在线状态，这些**只能自己设计**。

### 4.7 隐私与账号管理

| 能力 | 有做的项目 |
|---|---|
| 注销账号 | CRMEB、ShopXO（合规要求，2023 后必须有） |
| 隐私设置（不被搜索等） | **都没有** |
| 消息通知开关 | 少数有 |
| 第三方登录解绑 | CRMEB |

**注销账号是合规硬要求**，我们已经做了 ✅
**隐私设置商城系统不做，但社交产品必须做** —— 我们已做 ✅

## 五、横向总结：我们该学什么、不该学什么

### ✅ 该学（而且我们缺）

| 项 | 来自 | 优先级 |
|---|---|---|
| **收货地址管理**（省市区三级联动 + 默认地址） | 全部五个 | **高**——购物 App 的刚需，我们现在完全没有 |
| **最后登录时间 / 在线状态**展示到列表 | 全部五个都有字段 | 中——我们已建模，未展示 |
| **账号状态**（正常/禁用/注销中） | 全部五个 | 中——注销流程需要它 |
| **Token 过期与刷新**的接口预留 | CRMEB / ShopXO | 中——现在不做，但接口要留位置 |
| **登录失败次数限制** | ShopXO / CRMEB | 低——demo 可后置 |

### ❌ 不该学（对我们不合适）

| 项 | 为什么不做 |
|---|---|
| 会员等级 / 成长值 | 为促销服务，早期没有复购数据支撑 |
| 积分 / 优惠券 | 同上；且需要运营投入 |
| **余额 / 充值** | **资金池，强监管，个人主体绝对不能碰** |
| 分销 / 邀请返利 | **接近经营性，个人备案做不了** |
| 拼团 / 砍价 / 秒杀 | 营销工具，且秒杀对架构要求高，demo 阶段是负担 |
| 付费会员卡 | 需要企业主体与支付 |

### 🔀 商城系统不做、但我们必须做（我们的差异点）

因为这些是**社交产品**的能力，而我们的定位是「穿搭社区 + 购物」：

1. **关注 / 粉丝**（含关注列表、粉丝列表）
2. **私聊**（会话、历史消息、未读）
3. **拉黑 / 举报**
4. **在线状态 / 上次在线时间**（用户可见性受隐私控制）
5. **用户搜索**（按昵称 + 用户码）
6. **隐私设置**（不被搜索、隐藏在线、隐藏地区、陌生人私聊开关）

**这 6 项我们已经全部做了**（P0-2）。所以：
> 商城系统能教我们的是「**交易侧的用户数据**」（地址、账号状态、登录安全），
> 不能教我们「**社交侧的用户关系**」——那部分我们反而走在它们前面。

## 六、落到我们身上的行动项

按投入产出排序：

| 优先级 | 事项 | 依据 |
|---|---|---|
| **P0** | **收货地址管理**（增删改查 + 默认地址 + 省市区） | 五个项目全都有，我们完全没有；下单流程的硬前提 |
| **P0** | 用户表补 `status`（正常/禁用/注销中） | 注销流程需要中间态；商用项目全都有 |
| P1 | 个人主页与帖子展示「最后登录时间」 | 已建模未展示，工作量极小 |
| P1 | 收藏 / 浏览历史的**数据结构**（现在是假数字） | 五个项目都有真实表结构 |
| P2 | 登录接口预留 `refreshToken` 与失败限流 | 现在不做，接口留位 |
| — | 等级 / 积分 / 余额 / 分销 | **明确不做**，理由见上 |
